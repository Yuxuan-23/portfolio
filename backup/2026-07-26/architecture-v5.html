重点讲清业务知识如何进入系统，并稳定完成任务

建议用时：90 秒。关键词：场景抽象、用户交互、可解释结果。

讲解稿

这套架构首先解决的不是模型选型，而是不同业务场景需要不同输入字段和排查路径的问题。我把场景、入口字段、节点检索方式和跨节点关联规则抽象成可维护资产。运行时由固定 Workflow 保证场景确认、证据采集和报告门禁，Skill 只处理需要专业判断的步骤。最终输出不只是一个答案，而是候选原因、证据引用和待核动作。当前 Demo 重点验证了前端配置方式和用户诊断流程，平台化 Runtime 是后续产品升级设计。

优先展示

  • 场景资产工作台和动态入口字段
  • 从自然语言问题到诊断任务的转换
  • 证据卡、人工复核和下一步动作

常见追问

  • 业务人员是否需要填写 JSON
  • 新增场景如何减少开发依赖
  • 结果不确定时如何表达

重点讲清确定性骨架与动态能力之间的运行时边界

建议用时：120 秒。关键词：Harness、上下文投影、工具治理、Trace。

讲解稿

我把平台运行机制拆成四层。Workflow 保留不可跳过的确定性步骤，Skill Registry 管理可复用的诊断方法，Context Projector 只向当前 Skill 投影最小必要上下文，MCP Runtime 负责工具发现、参数校验、权限和执行。Skill 决定为什么调用工具，MCP 决定如何安全调用。每一步的场景版本、能力版本、派生字段、证据引用和跳过原因进入 Diagnostic Trace，后续评测可以把失败归因到配置、Skill、工具、上下文或流程，而不是只判断最终答案对错。

优先展示

  • Workflow、Skill 与 MCP 的职责边界
  • Run Context 与 Working State 的拆分
  • Trace、评测、版本和回放闭环

常见追问

  • 为什么不用一个大 Prompt
  • 上下文如何避免无限增长
  • Skill 与 MCP 为什么不能合并

重点讲清非完整 Trace 条件下的跨系统取证与关联

建议用时：90 秒。关键词：动态字段、逐跳关联、证据链、迁移能力。

讲解稿

真实故障并不总有完整 Trace ID，所以我没有把诊断能力建立在单一链路标识上。每个节点维护可接受的检索键、可提取的新标识和下一跳映射，运行时通过 Correlation Ledger 记录手机号、柜员号、请求号、局部 Trace 等标识的来源和转换证据。关联中断或多命中时系统不会强行串链，而是保留候选并请求补充信息。这套抽象可以迁移到客服、风控、交付治理和其他需要跨系统取证的复杂场景。

优先展示

  • Node Query Recipe 与 Correlation Plan
  • Trace 中断、多命中和缺字段策略
  • 证据引用与人工复核边界

常见追问

  • 没有全链路 Trace 怎么关联
  • 字段类型和数量变化怎么处理
  • 如何控制误关联和误判

重点讲清你负责产品机制设计，不把架构方案包装成生产实现

建议用时：75 秒。关键词：职责边界、接口合同、安全、工程可行性。

讲解稿

我的工作重点是把专家排障过程抽象成可实现的对象、状态和协作合同。场景资产定义输入与链路，Workflow 定义不可跳过的执行门禁，Skill 定义诊断方法，MCP Runtime 定义受控工具访问，Trace 定义可审计的运行记录。我不会把这些内容表述为已经完成的生产后端。当前可验证的是交互原型、配置模型和诊断路径，后续落地需要与研发共同细化存储、调度、权限、可观测性和性能方案。

优先展示

  • 对象边界和运行时职责
  • 凭据、敏感字段与只读工具策略
  • 从 Demo 到生产化的工程拆分

避免误区

  • 不声称独立完成全部后端
  • 不把前端模拟称为生产接入
  • 不回避性能、权限和稳定性问题
