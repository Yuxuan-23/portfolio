核心判断

平台能力不是组件数量，而是四个可验证的产品选择

我重点处理的不是模型如何回答，而是业务知识如何进入系统、能力如何扩展、工具如何受控、质量如何持续治理。

业务抽象与规模化

把专家经验转成可维护的场景资产

业务人员维护场景与入口字段，技术人员维护链路、节点检索和字段接力。新增场景不再依赖手写 JSON 或复制整套流程。

代表产物 Scene Package、链路拓扑、节点检索配方、跨节点关联计划
Agent 边界

固定主流程，按证据调度专业能力

场景确认、证据采集和报告门禁不可跳过。专项 Skill 只有在证据满足条件时才触发。

证明：路径可回放，未触发分支有原因
企业连接

Skill 管诊断方法，MCP 管工具访问

能力不保存生产地址和凭据。工具运行时统一处理权限、参数校验、超时和错误。

证明：工具可替换，诊断合同保持稳定
运行时与质量

上下文、证据与评测形成同一条闭环

每个 Skill 只获得最小必要上下文。原始日志进入证据存储，工作状态只保留摘要和引用。Trace 记录场景版本、能力版本、工具调用和结论门禁，失败可以归因并进入回归。

证明：不是一次性回答，而是可以治理和迭代的企业 Agent 运行机制

架构能力必须落到一条真实可解释的路径

手机银行登录案例不用于证明组件齐全，而用于证明系统知道何时继续、何时停止、为什么得出当前判断。

上下文构建从模糊报错、环境和入口关键字形成可执行的诊断任务。
跨节点取证沿业务链路检索日志并派生技术标识，避免只依赖用户直接提供 Trace ID。
条件能力调度证据不满足时跳过网络与系统诊断，并在 Trace 中记录原因。
报告门禁RPC 超时保留为候选原因，不直接升级为确定网络根因。
